## 3. 승인의 조건

### P2

FOLLOWUP-001 3장 2번("물리 parameter는 바꾸지 않는다")은 결과를 본 뒤 숫자를 맞추는 일을 막기 위한 규칙이다. P2는 실제 model 결과가 나오기 전의 변경이고, 정답지를 더 정확하게 만드는 것이므로 이 규칙의 예외로 둔다. 예외는 `regimes.CC.pre_s`와 `regimes.CC.observe_s` 두 값에만 적용한다.

재생성 후 다음을 확인하고 `scenarios/GENERATION_REPORT.md`에 수치로 남긴다.

1. CC의 SOC0, ST 시나리오의 consistent set이 모두 `{SOC0, ST}`이다.
2. 같은 시나리오의 delta chi2에서 p < 0.05로 구분되는 비율이 small, large 모두 우연 수준(약 5%)이다.
3. CC의 R0, TB 시나리오의 consistent set이 심은 cause 하나다. 관측 구간이 600 s로 줄어도 R0의 온도 신호가 clear reject 기준을 넘는지 본다.
4. 모든 not identifiable 시나리오에 resolving experiment가 있고, 대표 실험 중 SOC 기준으로 거부되는 것의 목록을 낸다.

하나라도 실패하면 임계값이나 다른 parameter를 고치지 말고 수치와 함께 보고한다.

### thinking 요약

제안이 쓴 설정(`thinking: {type: adaptive, display: summarized}`)이 실제 API에 있는지 검토자가 확인하지 못했다. 공식 문서에서 확인하고, P6의 실호출에서 두 model이 모두 받는지 확인한 뒤에 넣는다. 확인되지 않으면 넣지 않는다. 이 설정이 답의 내용을 바꾸는 것으로 문서에 나와 있으면 넣기 전에 보고한다.

### pilot

- `--yes`를 붙인 실제 호출은 P6의 점검을 포함해 사용자 승인 뒤에 한다.
- pilot 결과를 본 뒤에는 시나리오, 임계값, 채점 규칙, prompt를 고정한다. invalid 비율이 10%를 넘는 경우만 예외이고, 그때도 먼저 보고한다.
- 본 실행의 repeats 수는 pilot의 실측 비용과 호출당 시간을 보고 사용자가 정한다.

## 4. 추가 사항

### D1. 조합 단위 통계 (필수)

not identifiable 24개는 실질적으로 네 가지 설계(SOC0 / ST × small / large)의 noise 반복이다.

- `summary.md`의 모든 비율에 (regime, cause, size) 조합 단위로 묶은 bootstrap 구간을 함께 낸다.
- 표의 주석과 README에 "not identifiable 24개는 4가지 설계 × 6회"라고 적는다.
- 완료 보고의 결론 문장은 조합 단위 구간을 기준으로 쓴다.

### D2. CC의 SOC0, ST 크기 연속화 (조건부)

P2를 적용하면 CC의 SOC0와 ST는 크기와 무관하게 겹친다. 그래서 이 24개에 한해 target shift를 6–20 mV의 연속값으로 뽑아도 7.4 검증이 깨질 위험이 작다. 네 가지 설계의 반복이라는 약점을 줄일 수 있다.

- 작업량을 먼저 추정한다. 반나절 안에 끝나고 3장 P2의 확인 항목을 모두 통과하면 적용한다.
- 그렇지 않으면 하지 않고, 추정한 작업량과 이유만 보고한다.
- 적용하더라도 DYN과 CC의 다른 cause는 바꾸지 않는다. 지표를 small / large로 나눠 내는 표는 크기 구간(예: 13 mV 미만 / 이상)으로 바꾼다.

### D3. 표현

P4에 따라 "실험 선택을 측정한다"는 주장은 약해진다. README와 보고서에서 실험 선택은 보조 지표로 적고, 무작위 기준선 95%를 같은 자리에 적는다. pitch와 deck의 해당 문구는 사용자가 따로 고친다.

## 6. 그대로 유지되는 규칙

- API key는 환경 변수 `ANTHROPIC_API_KEY`에서만 읽고 어디에도 기록하지 않는다.
- oracle 임계값(1.15, 1.50, noise ratio 1.5)과 `rms_mode`는 바꾸지 않는다.
- `results/`의 기존 run은 지우거나 덮어쓰지 않는다.
- commit과 push는 사용자가 요청할 때만 한다.
- 기대와 다른 결과도 그대로 보고한다. 결과를 보고 시나리오를 더 어렵게 만들지 않는다.
